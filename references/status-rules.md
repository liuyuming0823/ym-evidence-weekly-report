# 四态判定规则

判定依据只有一个：**有没有结果证据**。不是「有没有提到这件事」，也不是「做没做过动作」。

## 状态定义

| 状态 | 判定标准 | 典型措辞 | 归属段落 |
|---|---|---|---|
| 已完成 | 有明确结果证据：上线、合并、通过、交付、关闭、「已…」+ 结果 | 「已上线」「合并到 master」「测试通过」「交付给 XX」 | 本周完成 |
| 进行中 | 有动作描述但无结果 | 「在改」「排查中」「做到一半」「进行到 XX 步」 | 进行中 |
| 阻塞 | 有阻碍描述，且未解决 | 「等 XX 回复」「权限没开」「卡在 XX」 | 阻塞与需支持 |
| 计划 | 仅表达意图，动作尚未开始 | 「准备」「打算」「下周做」「计划」 | 下周计划 |

## 判定示例

| 原始记录 | 判定 | 理由 |
|---|---|---|
| 「把登录接口改成 token 方式，已联调通过」 | 已完成 | 有「联调通过」这一结果 |
| 「把登录接口改成 token 方式」 | 进行中 | 只有动作，没说结果 |
| 「在改登录接口，等运维开环境」 | 阻塞 | 明确说了卡点 |
| 「下周把登录接口改成 token 方式」 | 计划 | 动作尚未开始 |
| 「登录接口这块后续要重构一下」 | 计划 | 「后续要」是意图 |

## 容易判错的三种情况

1. **「完成」出现在任务名里** — 如「完成登录重构任务」，这是任务标题不是结果，若没有结果描述判为进行中。
2. **百分比进度** — 「XX 功能做了 80%」属进行中，不算完成，除非明确说剩余部分已交付。
3. **未验证的完成** — 「改完了，还没测」应判为进行中，并在报告里注明「未验证」。

## 来源编号规则

- 按用户输入顺序编号，从「记录 1」开始
- 一条记录涉及多个事项时，拆成多条结论但沿用同一编号
- 用户未提供日期时，报告开头统一标注「用户未提供日期，按输入顺序编号」
- 同一条记录不可能既支撑「本周完成」又支撑「下周计划」，出现这种情况说明判定错了，回到上表重新判
